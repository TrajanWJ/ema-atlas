# Plan: EMA v1.1 Track E — Knowledge / Blueprint / Intentions / Graph / Research / Canon

**Generated**: 2026-04-13
**Estimated Complexity**: Very High
**Planning Mode**: Full-program / self-paced / canon-first

## Executive answer
No — not all EMA meta knowledge is fully inside EMA’s own system yet.

Right now, EMA meta knowledge is spread across:
- local architecture and boundary docs
- wiki mirrors
- implementation notes
- planning files
- research files
- runtime/control-plane state
- transitional surface memory

Track E should make EMA capable of ingesting and governing its own meta knowledge as first-class canon, claims, observations, blueprints, intents, contradictions, and projections.

The goal is:
**EMA should be able to model itself, plan itself, inspect itself, explain itself, and evolve itself from inside its own knowledge system without collapsing canon, planning, reality, and surface projections into one blob.**

---

## Overview

Track E is the semantic-operational knowledge layer for EMA v1.1.

It must support all known EMA layers so far:
- canon plane
- intention-building plane
- operational planning plane
- runtime / execution plane
- reality / implementation plane
- review / provenance plane
- gap / contradiction plane
- surface / read-model plane

Track E must not only hold knowledge about projects or external systems.
It must hold **EMA meta knowledge about EMA itself**.

That means the graph/canon layer must model:
- architectural truth
- implementation reality
- active intent coordination
- blueprint formation
- runtime proposals/executions/results
- review/provenance/promotions
- contradictions and unresolved gaps
- surface honesty/read models
- imported research and external inspiration
- cross-pollination across tracks and products
- planning artifacts and calendarized work

This plan assumes Track E is implemented as a **multi-layer knowledge/control subsystem** rather than a cosmetic graph feature.

## Planning assumptions

### Grounded in current EMA docs
This plan is aligned with local workspace docs indicating:
- EMA is canonical host control plane
- wiki is semantic memory substrate
- surfaces are projections, not authorities
- intention-building is distinct from canon and runtime execution
- gaps/contradictions are first-class
- blueprint planning should remain explicit and promotable

### Product assumptions
Track E should support:
- human operator use
- agent use
- CLI and GUI use
- read-model surfaces
- blueprint/graph visual work
- durable evidence/provenance
- incremental canon governance

### External pattern donor assumptions
Track E should deliberately absorb useful patterns from:
- **GitNexus** — local code intelligence, MCP query tools, multi-repo grouping, blast-radius/impact workflows, auto wiki generation, global indexed registry
- **graphify** — multimodal ingestion, deterministic extraction + semantic extraction pass, confidence-tagged edges, persistent graph artifacts, graph report summaries, graph-first assistant orientation, query/path/explain workflows, watch/update mode

Track E should absorb the useful ideas without becoming a clone of either.

## Goals

1. Make EMA meta knowledge representable inside EMA.
2. Build a typed object graph that spans all known EMA planes.
3. Introduce governed canon, trust, freshness, contradiction, and supersession.
4. Support blueprint formation without polluting canon.
5. Support feeds/wiki/graph as projections over shared truth.
6. Support research import and cross-pollination.
7. Support planning artifacts, virtual calendar pacing, phases, tasks, and subprojects as first-class linked objects.
8. Cover core GitNexus and graphify use cases where they make EMA stronger.
9. Preserve human legibility and operator usefulness.
10. Avoid graph-spaghetti and parallel truth stores.

---

## Non-goals

1. Replace all runtime state with a graph write path.
2. Force all thought into canon immediately.
3. Collapse planning, canon, and reality into one undifferentiated store.
4. Build a decorative graph with no operator value.
5. Ship every advanced inference feature in v1.

Governed, durable knowledge:
- intents
- concepts
- artifacts

- accepted claims

### Layer 4 — Projection/read-models
Derived operator-facing surfaces:
- blueprint views
- feeds
- wiki pages
- graph perspectives
- cross-pollination suggestions
- current-state projections

## Subprojects

Deliver research ingestion, claim extraction, import suggestions, and reusable pattern transfer.

Ingest EMA’s own architecture/planning/reality/provenance docs and represent them inside Track E.

Model phases, tasks, dependencies, subprojects, virtual calendar, and milestone pacing inside the same graph.

Map GitNexus and graphify patterns into EMA-native capabilities and gap coverage.

Measure quality, correctness, trust, freshness, usefulness, and operator success.

## Risks and gotchas

### Risk 1: Meta knowledge remains split across docs and system
**Mitigation:** make meta-EMA ingestion a dedicated subproject, not a nice-to-have.

### Risk 2: Canon and planning get collapsed
**Mitigation:** preserve plane discipline and promotion boundaries.

### Risk 3: Graph becomes visually impressive but operationally useless
**Mitigation:** prioritize feeds, query paths, contradictions, and operator questions.

### Risk 4: Over-modeling slows delivery
**Mitigation:** keep day-one ontology small; add day-two concepts later.

### Risk 5: External donor pattern overload
**Mitigation:** use adoption/defer/reject matrix; do not clone entire products.

### Risk 6: Calendar/planning graph becomes stale immediately
**Mitigation:** use self-paced phase states and review cadence instead of brittle exact-date scheduling.

---

## Rollback plan

If Track E scope gets too wide:

2. keep blueprint + feed + wiki minimum surfaces
3. defer deep research import and code-intelligence parity
4. defer advanced multi-repo and multimodal ingest
5. keep meta-EMA doc ingestion and contradiction tracking as mandatory minimum
