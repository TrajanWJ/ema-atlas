# Proposal Lifecycle State Machine in proposal-state.json

> The proposal lifecycle state machine is the backbone of the dispatch system's self-improvement capability. Without it, proposals are fire-and-forget. With it, the system learns which engines produce valuable work and which generate noise.

## Executive Summary

`dispatch/proposal-state.json` implements a finite state machine that tracks every proposal from generation through execution to outcome. Each proposal transitions through three core states — `proposed`, `dispatched`, `completed` — with terminal outcomes of `success` or `fail`. This creates a closed feedback loop: proposal engines generate work, the dispatch layer executes it, and outcomes flow back to inform future proposal quality.

---

## State Machine Definition

### States

| State | Meaning | Entry Condition |
|-------|---------|-----------------|
| `proposed` | Generated by a proposal engine, awaiting review or auto-dispatch | Engine creates a new entry |
| `dispatched` | Approved and sent to dispatch for execution | Manual approval or autonomy-rule auto-approval |
| `completed` | Execution finished, outcome recorded | Task IDs matched in `dispatch/done/` |

### Transitions

```
proposed ──→ dispatched ──→ completed (success)
    │              │
    │              └──→ completed (fail)
    │
    └──→ expired (implicit — stale proposals never dispatched)
```

### Terminal Outcomes

- **success** — all associated tasks completed with acceptable results
- **fail** — one or more tasks failed, timed out, or produced unacceptable results
- **null** — still in progress (dispatched but not yet completed)

---

## Schema Per Entry

Each proposal entry in the `proposals[]` array carries:

```json
{
  "id": "prop-{unix_timestamp}-{8char_hex}",
  "title": "Imperative description of work",
  "source": "engine that generated this proposal",
  "priority": "P0–P4",
  "state": "proposed | dispatched | completed",
  "generated_at": "ISO8601",
  "dispatched_at": "ISO8601 | null",
  "task_ids": ["task-{hex}", ...],
  "outcome": "success | fail | null",
  "completed_at": "ISO8601 | null"
}
```

Key design choices:

- **`task_ids[]`** links proposals to actual dispatch tasks, enabling outcome tracking by scanning `dispatch/done/` for matching files
- **`source`** identifies which engine produced the proposal (pattern-recognition, vault-integration, self-improvement, etc.)
- **Timestamps at each transition** allow latency analysis and stale-proposal detection

---

## How the Feedback Loop Works

The state machine's primary value is closing the loop between proposal generation and outcome evaluation.

### Step 1: Generation
A proposal engine (e.g., pattern-recognition, vault-integration, self-improvement) generates a proposal and writes it to `proposal-state.json` with `state: "proposed"`.

### Step 2: Dispatch
The proposal is either auto-approved (per [[Autonomy Rules Table — Structured Classification of What Auto-Approves vs Requires Human Review|autonomy rules]]) or manually approved. On dispatch, the entry updates to `state: "dispatched"`, `dispatched_at` is set, and `task_ids` are populated with the IDs of tasks created in the dispatch queue.

### Step 3: Outcome Scanning
On each proposal-engine run, the `check_completed_outcomes()` function scans `dispatch/done/*.json`, matches task IDs against `proposal-state.json` entries, and updates `state` → `completed` with the appropriate `outcome` and `completed_at` timestamp. This is the [[Feedback Loop Pattern|feedback loop pattern]] — the engine reads its own results before generating new proposals.

### Step 4: Learning
The self-improvement engine reads completed proposals to determine:
- Which source engines produce high-success proposals
- Which proposal types consistently fail
- Whether specific priority tiers or scope sizes correlate with outcomes
- Where the system is generating noise vs. value

### Capacity Control

The state machine integrates with the [[Active Large Proposal Cap|active large-proposal cap]] — when 3+ large proposals are in `dispatched` state, new large proposal generation is blocked. This prevents queue overload and ensures the system doesn't generate faster than it can execute.

## Why a State Machine (Not Just a Log)

A simpler design would just log proposals to a JSONL file. The state machine is better because:

1. **Queryable state** — "how many proposals are in-flight?" is a JSON filter, not a log scan
2. **Idempotent updates** — re-running outcome scanning doesn't create duplicates
3. **Capacity enforcement** — the cap logic needs to count active proposals by state
4. **Feedback attribution** — linking outcomes back to source engines requires mutable state
5. **Lifecycle visibility** — operators can see the full pipeline at a glance

The tradeoff is that `proposal-state.json` is mutable shared state — concurrent writers need care. In practice, the proposal engine runs sequentially (not parallel), so this is acceptable.

---

## Relationship to the Extended Schema

The [[Extended Proposal JSON Schema with Backwards-Compatible Fields|v2 proposal schema]] adds richer fields (`scope`, structured `source`, `tasks[]`, `success_criteria[]`, `impact`) to individual proposals. The state machine in `proposal-state.json` is complementary — it tracks lifecycle state across all proposals regardless of schema version. A v1-format proposal and a v2-format proposal both flow through the same `proposed → dispatched → completed` lifecycle.

The v2 `success_criteria[]` field makes the state machine's outcome determination more precise: instead of inferring success from task completion status alone, the system can verify specific criteria were met.

---

## Design Lessons

### 1. Mutable state enables learning
Append-only logs are simpler but make feedback attribution expensive. The state machine trades simplicity for learnability.

### 2. Outcome scanning should be the first step, not the last
Running `check_completed_outcomes()` at the start of each engine invocation ensures the engine always has up-to-date outcome data before generating new proposals.

### 3. Source attribution is non-optional
Without knowing which engine produced a proposal, outcome data is useless for improvement. The `source` field is load-bearing.

### 4. State machines need garbage collection
Proposals stuck in `dispatched` indefinitely (orphaned tasks, crashed agents) need expiration logic. This is a known gap.

---

## Risks and Known Gaps

- **No expiration for stale dispatched proposals** — if a task crashes without writing to `done/`, the proposal stays `dispatched` forever
- **Single-file concurrency** — `proposal-state.json` is a shared mutable file; concurrent proposal engines would need locking
- **Outcome binary is reductive** — success/fail doesn't capture partial success or "completed but low quality"
- **No schema version field** — as the state file evolves, there's no version marker to guide migrations
