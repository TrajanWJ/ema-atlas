Architecture: How should the simulation engine work?

All three share the same UI (civilization map + nav views + /mapfree dashboard). The difference is how the brain works.

A

Turn-Based State Machine (Recommended)

A central SimulationEngine drives everything. Each "turn" is a discrete cycle: pick an agent → build context (constitution + registry + recent history) → call Claude API → parse structured JSON response → execute MODIFY_REGISTRY actions → update map → next turn. Pause/unpause controls the loop. Save/load serializes the full registry + constitution + turn history to IndexedDB.

Pros

  • Deterministic, debuggable — each turn is a clean state transition
  • Natural pause/resume — just stop the loop
  • Save/load is trivial — serialize the state tree
  • Maps perfectly to your Autopoiesis Node concept
  • Rate-limit friendly — one API call per turn

Cons

  • Slower pacing — one agent acts at a time
  • Less "alive" feeling between turns

💡 This is the approach from your Autopoiesis Node docs. It's proven and maps cleanly to the UI.

B

Event-Sourced Stream

Instead of turns, the system emits events (AgentCreated, RuleProposed, VoteCompleted, DepartmentEstablished). A central event store is the source of truth. The registry, map, and all views are projections of the event stream. Multiple agents can deliberate concurrently via parallel API calls. The UI subscribes to the event stream and updates reactively.

Pros

  • Feels more alive — multiple things happening at once
  • Timeline view comes free — just replay the event log
  • Perfect undo/redo — replay events up to any point
  • More architecturally impressive for a portfolio

Cons

  • More complex to build — event sourcing has real engineering overhead
  • Concurrent API calls = higher cost and harder to rate-limit
  • Race conditions possible in registry mutations
C

Hybrid: Turn-Based Core + Event Stream UI

The simulation engine runs turn-based (one agent per turn, clean state transitions), but every mutation emits an event to a log. The UI consumes the event stream reactively — so the map animates smoothly, the timeline builds itself, and views update in real-time. Best of both: simple engine, rich UI.

Pros

  • Simple engine (turn-based) with rich UI (event-driven)
  • Timeline and undo come from the event log
  • Rate-limit friendly — still one API call per turn
  • Save/load = serialize state + event log
  • Feels alive because events animate the map between turns

Cons

  • Two mental models (turns for engine, events for UI)
  • Slightly more code than pure turn-based

💡 Recommended — gives you the portfolio-impressive event architecture without the complexity of true concurrent agents.
