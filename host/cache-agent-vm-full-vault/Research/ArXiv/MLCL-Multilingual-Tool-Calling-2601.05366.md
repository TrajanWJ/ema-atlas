# Lost in Execution: On the Multilingual Robustness of Tool Calling in Large Language Models

**Paper:** arXiv:2601.05366 (submitted 2026-01-08)
**Authors:** Zheng Luo (USC), T Pranav Kutralingam, Ogochukwu N Okoani, Wanpeng Xu, Hua Wei, Xiyang Hu (Arizona State University)
**Source:** https://arxiv.org/abs/2601.05366

## Key Finding

Multilingual tool-calling failures are primarily driven by **execution-interface violations** (parameter values in the wrong language), not by failures in intent understanding or tool selection. Models often select the correct tool and generate semantically appropriate arguments, but produce parameter values in the user's language rather than the English required by execution interfaces.

---

## 1. The MLCL Benchmark

### Base Dataset
- Built on top of **BFCL V4** (Berkeley Function Calling Leaderboard), specifically the `BFCL_v4_multiple.json` subset
- Single-turn queries paired with multiple candidate functions
- Execution interface kept language-invariant and English-only throughout

### Languages Evaluated
| Language | Type | Script | Rationale |
|----------|------|--------|-----------|
| **English** | Reference baseline | Latin | Control condition |
| **Chinese (ZH)** | High-resource | Logographic | Abundant training data |
| **Hindi (HI)** | Mid-resource | Devanagari | Richer morphology, flexible word order |
| **Igbo (IG)** | Low-resource | Latin | Limited representation in training data |

### Two Diagnostic Dimensions

**Query Language Composition** (how non-English content enters the query):
- **NT (Not Translated):** Original English queries (baseline)
- **PAR (Partially Translated):** Surrounding context translated, but ground-truth parameter values remain in English (mixed-language)
- **FT (Fully Translated):** Entire user query translated to target language

**Semantic Perturbation Design** (surface-form variations preserving intent):
- **NO:** No perturbation (original wording)
- **PARA:** Paraphrased versions with altered phrasing but unchanged meaning
- **SYNO:** Synonym substitutions on individual words

Translations generated by GPT-5 and manually verified by native speakers for semantic equivalence.

### Dataset Size
Based on BFCL V4 multiple-function subset. Each English query generates variants across 3 languages x 3 composition types x 3 perturbation types = 27 non-English conditions per query, plus the English baselines.

## 2. Failure Modes and Error Taxonomy

### Error Categories (ordered by severity, most to least severe)

**Execution-blocking errors:**
1. **Syntax Error** -- Malformed tool call that cannot be parsed (e.g., `get_forecast(location ="new york city")`)
2. **Function-Level Error** -- Syntactically valid but violates schema: wrong function name, missing parameters (e.g., `event_search(location="NYC")` when `get_forecast` was needed)

**Parameter value language mismatch** (the central finding, three sub-types):
3. **Language Mismatch: Wrong Value** -- Non-English parameter value with irrelevant meaning (e.g., location="纽约地铁站" [NYC subway station] instead of "New York City")
4. **Language Mismatch: Related but Incorrect** -- Non-English value related but semantically imprecise (e.g., location="纽约万豪酒店" [NYC Marriott Hotel])
5. **Language Mismatch: Same Meaning** -- Non-English value with correct meaning but wrong language (e.g., location="纽约市" [New York City in Chinese]). Semantically correct, but fails execution because the interface expects English.

**English-language parameter errors (no language mismatch):**
6. **Wrong Value** -- English but semantically incorrect (e.g., "Los Angeles" instead of "New York")
7. **Related but Incorrect** -- English, related but not exact (e.g., "New York" vs. ground truth requiring more specificity)
8. **Same Meaning** -- English, semantically correct but different surface form (e.g., "NYC" vs. "New York City")

### The Dominant Failure Mode: Parameter Value Language Mismatch

This is the paper's central contribution. In multilingual settings:
- Models correctly identify the function to call
- Models correctly identify which parameters to fill
- Models generate semantically appropriate values
- **But values are in the user's query language, not the English required by the tool interface**

Example from Figure 1:
- English query: `humidity_temperature_forecast(location="New York City", days=7)` -- EXECUTES
- Chinese query: `humidity_temperature_forecast(location="纽约市", days=7)` -- FAILS (correct meaning, wrong language)
- Hindi query: `humidity_temperature_forecast(location="न्यू यॉर्क सिटी", days=7)` -- FAILS (transliteration error)
- Igbo query: `humidity_temperature_forecast(location="New York obodo", days=7)` -- FAILS (nonstandard parameter with "obodo" = "city" in Igbo)

## 4. Key Quantitative Results

### Error Rates from Figures (representative models, FT setting, no semantic perturbation)

**English (NT) baseline error rates:**
- DeepSeek V3.2: ~0.100
- GPT-5: ~0.135
- Llama 3.1-70B: ~0.140
- Qwen3-Next-80B: ~0.190
- Granite 4.0-h-small: ~0.110

**Chinese (FT) error rates:**
- DeepSeek V3.2: ~0.535 (language mismatch dominant)
- GPT-5: ~0.470
- Llama 3.1-8B: ~0.490, 70B: ~0.520
- Qwen3-8B: ~0.535, Qwen3-32B: ~0.455
- Granite 4.0-h-tiny: ~0.245, h-small: ~0.305

**Hindi (FT) error rates:**
- DeepSeek V3.2: ~0.440-0.435
- GPT-5: ~0.375
- Llama 3.1-70B: ~0.375
- Qwen3-Next-80B: ~0.355
- Granite 4.0-h-small: ~0.270

**Igbo (FT) error rates:**
- DeepSeek V3.2: ~0.263
- GPT-5: ~0.285
- Llama 3.1-70B: ~0.310
- Qwen3 models: ~0.275-0.485

### Key Patterns

1. **FT universally increases error rates** across all models and languages, roughly 2-4x over English baselines
2. **Chinese shows highest language mismatch**: Models are most likely to copy Chinese tokens into parameter values because Chinese has abundant training data and the model "fluently" mirrors it
3. **Hindi shows moderate mismatch**: Similar pattern to Chinese but with transliteration errors added
4. **Igbo shows lowest language mismatch but highest semantic errors**: Models rarely copy Igbo tokens (low-resource = less fluent mirroring), but instead produce more query-understanding errors
5. **PAR substantially reduces language mismatch**: By preserving English parameter strings in the query, PAR error rates often approach or match English NT baselines for strong models like GPT-5 and Llama 3.1-70B

### Semantic Perturbation Effects
- In English (NT): PARA and SYNO substantially increase errors (strict surface-form matching fails)
- In FT: Semantic perturbations have limited additional impact -- errors already dominated by language mismatch
- In PAR: Intermediate sensitivity -- perturbations can replace preserved English strings with non-English equivalents, reintroducing mismatch

## 5. Inference-Time Mitigation Strategies

### Three Strategies Evaluated

**PT (Prompt-Level Instruction):**
- Adds explicit instruction: "IMPORTANT: Pass all parameter values in English"
- Translates user query to target language but instructs English-only output
- Result: Reduces language mismatch relative to FT, but compliance is inconsistent and residual mismatches remain common

**PRE (Pre-Translation of User Queries):**
- Translates non-English queries into English before tool calling (same model does both translation and tool calling)
- Serves as upper bound on input normalization
- Result: Most effective strategy overall. Removes multilingual variation from the tool-calling step entirely. But introduces semantic drift and surface-form normalization that creates NEW execution errors

**POST (Post-Translation of Parameter Values):**
- Generates tool call normally, then translates non-English parameter values to English before execution
- Directly targets language mismatch while preserving original tool/argument selection
- Result: Effective at fixing language mismatch specifically, but less effective than PRE because it lacks full query context

### Mitigation Results (DeepSeek V3.2, from Figure 6)

**Chinese:**
| Setting | Error Rate |
|---------|-----------|
| FT (no mitigation) | ~0.545 |
| PT (prompt instruction) | ~0.370 |
| PAR (partial translation) | ~0.335 |
| PRE (pre-translate query) | ~0.250 |
| POST (post-translate params) | ~0.270 |
| NT (English baseline) | ~0.100 |

**Hindi:**
| Setting | Error Rate |
|---------|-----------|
| FT (no mitigation) | ~0.400 |
| PT | ~0.370 |
| PRE | ~0.245 |
| POST | ~0.310 |
| NT (English baseline) | ~0.100 |

**Critical finding:** None of the strategies recover English-level performance. PRE gets closest but still leaves a ~15 percentage point gap over English baselines.

### Low-Resource Language (Igbo) Mitigation Behavior
- Translation-based mitigations (PT, PRE, POST) provide **limited benefit** for Igbo and can even **increase errors**
- Parameter value language mismatch is already rare for Igbo (models don't copy Igbo tokens)
- Remaining failures are dominated by query understanding errors, which translation doesn't fix
- From Figure 7: For DeepSeek on Igbo, POST error rate (~0.263) is similar to or worse than NT (~0.205)

## 6. Model-Family-Specific Observations

**GPT-5 family:**
- Consistent performance across model sizes (GPT-5, mini, nano)
- Low semantic error rates, indicating strong multilingual intent understanding
- Errors primarily driven by parameter value language mismatch in FT
- PAR and PT substantially reduce mismatch errors

**Llama 3.1:**
- Larger models (70B) show fewer syntax errors and stronger instruction following
- 70B shows better awareness of English parameter conventions
- Llama 3.1-70B has a quirk: outputs only integers for numeric values when ground truths are decimals
- Both 8B and 70B show combined parameter value language mismatch AND semantic errors in FT

**Qwen 3:**
- Strong language alignment but inconsistent execution-interface adherence
- MoE models (30B-A3B, Next-80B-A3B) do NOT show monotonic gains with scale
- MoE architecture may lack simultaneous expertise in multilingual understanding AND tool-calling format
- Qwen3-Next-80B-A3B performs best on Igbo specifically
- PT (explicit prompting) yields mixed results -- strong language alignment can conflict with execution requirements

**Granite 4:**
- Strong English tool-calling performance
- Less responsive to instruction-based mitigation (PT yields limited improvement)
- Likely reflects tighter coupling between tool execution patterns and training-time conventions
- Larger Granite models perform worse on Chinese but better on Igbo (inverse scaling)

## 7. Recommendations and Implications

### From the Paper

1. **Multilingual tool calling is a system-level challenge**, not just a model capability gap. The interface between natural language and programmatic execution is the bottleneck.

2. **Inference-time patching is insufficient.** PRE, POST, and PT all help but none fully recover English-level performance. They trade one error type for another (language mismatch for semantic drift).

3. **Execution-aware system design** is needed: aligning natural-language variability with programmatic interfaces requires changes beyond model weights.

4. **Different strategies needed for different language tiers:**
   - High-resource languages (Chinese, Hindi): Target language mismatch with PRE or POST
   - Low-resource languages (Igbo): Focus on improving query understanding instead

### Practical Best Practices (Inferred)

- **Pre-translate user queries to English** before tool calling for best overall mitigation
- **Combine PRE with POST** as a belt-and-suspenders approach (not tested in paper but logical)
- **Add explicit English-parameter instructions** in system prompts as a low-cost supplement
- **Design tool interfaces to accept multilingual parameter values** where possible (the paper notes this would eliminate the problem at the interface level)
- **Monitor for "same meaning, wrong language" errors** -- these are the most insidious because the model understood everything correctly but still fails execution
- **Test tool-calling systems with non-English queries** before deploying globally
- **Be aware that MoE models** may underperform dense models of similar effective size on multilingual tool calling

### Limitations Noted by Authors
- Evaluation limited to single-turn, predefined function interfaces (BFCL subset)
- Only 3 non-English languages tested
- Definition of execution correctness assumes English-only tool interfaces (a design choice, not universal)
- Inference-time strategies are intentionally simple diagnostic probes, not optimized solutions
- Results constrained to specific models evaluated
