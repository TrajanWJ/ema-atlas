## 1. Pre-Dispatch Intelligence

### Pattern: Classification-First Routing (Anthropic "Routing" workflow)
**Who uses it:** Anthropic's recommended pattern, used by their production customers in customer support and coding agents.
**What it is:** Before dispatching, classify the input into a discrete category, then route to a specialized handler. The classification can be LLM-based or algorithmic. Key insight: "optimizing for one kind of input can hurt performance on other inputs" — so routing exists to prevent this.
**Evidence:** Documented as a core production workflow. Anthropic specifically calls out routing easy questions to cheaper models (Haiku) and hard ones to capable models (Sonnet) as a proven cost/quality optimization.
**Mapping to personal agent:** Your current routing table (casual → direct, single-domain → specialist, 3+ → orchestrator) is essentially this pattern. What's missing: **a structured classification step before the routing decision.** Add a lightweight intent extraction that outputs: `{domain, complexity_estimate, requires_tools: bool, similar_past_tasks: []}` before hitting the routing table. This is the "gate" Anthropic describes between steps.

### Pattern: Complexity-Gated Dispatch
**Who uses it:** Anthropic's own recommendation; Claude Code's built-in subagent system.
**What it is:** Don't dispatch at all unless complexity warrants it. Anthropic's #1 recommendation: "find the simplest solution possible, and only increasing complexity when needed." Claude Code's Explore subagent even has explicit thoroughness levels: quick/medium/very thorough.
**Evidence:** "For many applications, optimizing single LLM calls with retrieval and in-context examples is usually enough." Their most successful customers avoided over-engineering.
**Mapping:** Add a "can I just handle this directly?" check before every dispatch. Score: 1-3 handle direct, 4-7 single specialist, 8-10 orchestrator. This fights the "routing rationalization" anti-pattern already identified in SOUL.md.

## 2. Prompt Construction for Sub-Agents

### Pattern: Scoped Context with Tool Constraints (Claude Code Subagents)
**Who uses it:** Claude Code's production subagent system.
**What it is:** Each subagent gets: (1) its own context window (isolated from parent), (2) a custom system prompt, (3) specific tool access restrictions, (4) independent permissions. The parent specifies the task, the subagent works independently and returns results.
**Evidence:** Claude Code ships with built-in subagents (Explore, Plan, general-purpose) that use this pattern in production. The Explore agent is read-only (denied Write/Edit), uses Haiku for speed. The Plan agent inherits the parent model but is also read-only.
**Key finding:** Tool restriction is as important as prompt quality. Giving a research agent write tools is actively harmful — it changes behavior, not just capability.
**Mapping:** When constructing task prompts for specialists:
- **Include:** Task description, success criteria, relevant context snippets (not full history), tool allowlist
- **Exclude:** Full conversation history, unrelated context, tools outside the domain
- **Isolate:** Each specialist gets its own context window — don't share the parent's full context

### Pattern: Agent-Computer Interface (ACI) Design
**Who uses it:** Anthropic's SWE-bench agent team.
**What it is:** Invest as much effort in tool documentation as you would in human-computer interfaces. Key principles: (1) make tools obvious to use from description alone, (2) use absolute paths instead of relative (they found models made mistakes with relative paths after changing directories), (3) "poka-yoke" tools — design them so mistakes are hard to make.
**Evidence:** "We actually spent more time optimizing our tools than the overall prompt" — Anthropic's SWE-bench team. Switching to absolute filepaths eliminated an entire class of errors.
