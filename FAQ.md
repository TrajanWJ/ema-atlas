# FAQ

Anticipated questions a fresh agent (or fresh human) will ask in the first
hour of joining this project. Answers point at the canonical doc rather than
duplicating its content.

## Orientation

**Q: Where do I start?**
A: [`MACBOOK_AGENT_HANDOFF_MASTER.md`](MACBOOK_AGENT_HANDOFF_MASTER.md), then
[`AGENT_QUICKREF.md`](AGENT_QUICKREF.md). If your machine isn't set up,
[`AGENT_BOOTSTRAP.md`](AGENT_BOOTSTRAP.md) instead.

**Q: What is this repo, in one sentence?**
A: A handoff archive + navigable graph + (in-progress) Next.js atlas app
for the long-running EMA / Hermes rewrite of a human+agent operating
environment. See [`README.md`](README.md).

**Q: Is this the EMA codebase?**
A: No. The canonical EMA codebase is `TrajanWJ/ema`. This repo is a
**map of** it — plus snapshots of the lineage that fed it. See
[`graph/nodes/codebase-ema.qmd`](graph/nodes/codebase-ema.qmd).

**Q: What does "EMA" stand for?**
A: Not defined as an acronym anywhere in the visible lineage. Treat it as
a proper noun referring to the Elixir/Phoenix daemon and the system of
record it owns. See [`GLOSSARY.md`](GLOSSARY.md).

**Q: What's the canonical rule?**
A: **EMA owns truth. Hermes owns execution. Surfaces do not own state.**
If anything seems to contradict it, the rule wins — file an entry in
[`OPEN_QUESTIONS.md`](OPEN_QUESTIONS.md) before "fixing".

## Working with the graph

**Q: How do I find the right branch for my task?**
A: Use [`AGENT_TRAVERSAL.md`](AGENT_TRAVERSAL.md): map your task to a topic
edge under [`graph/edges/`](graph/edges/), load only the primary nodes from
that edge, then `git show origin/<branch>:<key_artifact>`.

**Q: Should I check out a `codebase-*` branch?**
A: Almost never. The node body + `key_artifacts:` paths in
`graph/nodes/<branch>.qmd` are designed to give you what you need without
checking out. If they don't, fix the node before fixing your task.

**Q: I see something missing from a node — can I add to it?**
A: Yes, follow [`CONTRIBUTING_TO_GRAPH.md`](CONTRIBUTING_TO_GRAPH.md). Make
sure to update reciprocal edges and run `./scripts/check-graph.sh`.

**Q: What's the difference between `graph.json` and `SYSTEM_MANIFEST.json`?**
A: `SYSTEM_MANIFEST.json` is the lightweight build-time index (branch ↔ sha,
node frontmatter). `graph.json` is the rich consumer view used by the atlas
app — adds bodies, triples, topics, glossary, and open questions. Schemas
in [`LIB_DATA_CONTRACT.md`](LIB_DATA_CONTRACT.md).

## Building / running

**Q: How do I run the daemon locally?**
A: See [`AGENT_BOOTSTRAP.md`](AGENT_BOOTSTRAP.md) §B.5. You need the live
EMA repo (`gh repo clone TrajanWJ/ema`); the snapshot under `codebase-ema`
in this transfer pack is read-only.

**Q: What's the atlas app for?**
A: See [`README.md`](README.md) "Current center of gravity" and
[`ATLAS_NOTES.md`](ATLAS_NOTES.md). Top-level routes: `/`, `/parts`,
`/artifacts`, `/graph`, `/desktop`, `/docs`. Run `npm install && npm run dev`.

**Q: How does the app stay in sync with the graph?**
A: It builds against `graph.json`, regenerated by
`./scripts/graph-json.sh`. Recommended `prebuild`:
`check-graph.sh && manifest.sh && graph-json.sh && index.sh`. See
[`ATLAS_NOTES.md`](ATLAS_NOTES.md).

## Architecture

**Q: Why Elixir? Why not Rust/Go/Node?**
A: Daemon-first architecture, supervision/resilience, concurrency for
orchestration and sync, strong fit for long-lived control-plane logic.
See [`03-architectural-evolution-and-major-decisions.md`](03-architectural-evolution-and-major-decisions.md) §4.

**Q: Why P2P? Isn't a single-node daemon simpler?**
A: Organizations/spaces imply multi-user distributed reality; capability
locality matters; peer dispatch matters. **But** local semantics must be
crisp before P2P lands — see [`graph/edges/transport.md`](graph/edges/transport.md).

**Q: Where do docs/wiki/canvas live? In `event_log`?**
A: Open question — [`OPEN_QUESTIONS.md`](OPEN_QUESTIONS.md) Q2 + Q8.
Working assumption (subject to user decision): a separate CRDT-ish
collaboration plane with the daemon as auth gateway. See
[`graph/edges/collab.md`](graph/edges/collab.md).

**Q: What's a "vApp"?**
A: A virtual app inside the EMA shell, rendered by Launchpad / Virtual
Desktop. Examples: Wiki, Chat, Threads, Agent vEnv, Blueprint, Code, Files,
Images. See [`GLOSSARY.md`](GLOSSARY.md) and
[`05-fresh-context-project-app-model.md`](05-fresh-context-project-app-model.md).

**Q: Driver vs Provider vs Harness — what's the difference?**
A: A **provider** is a model API (Anthropic, OpenAI). A **harness** is the
execution shell around a model invocation (a CLI, an in-process runtime, a
peer worker). A **driver** is the EMA-side typed adapter that picks a
harness for a given dispatch. See [`GLOSSARY.md`](GLOSSARY.md) and
[`graph/edges/execution.md`](graph/edges/execution.md).

## Identity / scope

**Q: How do Projects, Spaces, and Organizations relate?**
A: Open question — [`OPEN_QUESTIONS.md`](OPEN_QUESTIONS.md) Q3. Working
framing in [`05-fresh-context-project-app-model.md`](05-fresh-context-project-app-model.md):
each EMA instance lives within a Project; Projects belong to an Org or to
a User; Spaces scope collaboration inside an Org.

**Q: What is a "Personal AI"?**
A: A user-level agent identity with implicit access to all
Projects/Spaces the user belongs to, gated by per-Org policy. Where it
runs is open question Q4. See
[`05-fresh-context-project-app-model.md`](05-fresh-context-project-app-model.md).

**Q: Are agents members of a Space?**
A: Open question — Q1 in [`OPEN_QUESTIONS.md`](OPEN_QUESTIONS.md). Working
assumption: yes, first-class. But this hasn't been decided.

## Process

**Q: Can I make a decision on an open question?**
A: Use [`howto/resolve-an-open-question.md`](howto/resolve-an-open-question.md).
Don't delete the entry; mark it resolved with a link to the decision doc.

**Q: I want to change a glossary term.**
A: Don't introduce synonyms — extend the existing definition in place.
See [`CONTRIBUTING_TO_GRAPH.md`](CONTRIBUTING_TO_GRAPH.md) §7.

**Q: I'm adding a new branch. What's the workflow?**
A: [`howto/add-a-branch.md`](howto/add-a-branch.md). The node file goes
in **first**, then the branch push, then the cross-references.

**Q: My commit broke `check-graph.sh`. Can I push anyway?**
A: The check script warns; it doesn't block. But fix the warning before
you push — the graph integrity is the whole point. See
[`CONTRIBUTING_TO_GRAPH.md`](CONTRIBUTING_TO_GRAPH.md) "Pre-commit checklist".

## Things people get wrong

**Q: "Surfaces are just UI, right? They can cache state for performance."**
A: They can cache for performance, they can't *own* it. Ownership means
"this is the truth and other layers reconcile to it". The truth lives in
EMA's `control_plane/event_log`. See
[`03-architectural-evolution-and-major-decisions.md`](03-architectural-evolution-and-major-decisions.md) §6.

**Q: "OpenClaw is the architecture."**
A: OpenClaw is **doctrine**, not architecture. Its patterns (roles,
handoffs, watchdogs) are already absorbed into EMA's `babysitter/`. Don't
resurrect the OpenClaw runtime. See
[`graph/nodes/lineage-openclaw.qmd`](graph/nodes/lineage-openclaw.qmd).

**Q: "Drivers and providers are the same thing."**
A: They are not. Conflating them was one of the named architecture
mistakes — see
[`MACBOOK_AGENT_HANDOFF_MASTER.md`](MACBOOK_AGENT_HANDOFF_MASTER.md) §20.

**Q: "Let's add P2P now to future-proof."**
A: Don't. The architecture warns explicitly against distributing
underdefined single-node semantics. Land local clarity first.
[`02-project-transfer-brief.md`](02-project-transfer-brief.md) §13 risk #6.
